# 系统化调试

## 概述

随意的修复不仅浪费时间，还会引入新的 bug。快速补丁往往掩盖了潜在的问题。

**核心原则：** 在尝试修复之前，务必找到根本原因。仅针对症状的修复即为失败。

**违反此流程的字面规定，即违背了调试的精神实质。**

## 铁律

```
未经根本原因调查，严禁修复
```

如果你尚未完成第一阶段，则不得提出任何修复方案。

## 何时使用

适用于**任何**技术问题：

- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况下使用：**

- 时间紧迫（紧急情况容易让人倾向于猜测）
- “只需一个快速修复”看起来显而易见
- 你已经尝试过多次修复
- 之前的修复未生效
- 你并未完全理解该问题

**以下情况切勿跳过：**

- 问题看似简单（简单的 bug 也有根本原因）
- 你赶时间（匆忙必然导致返工）
- 经理要求立即修复（系统化方法比盲目试错更快）

## 四个阶段

在进入下一阶段之前，你**必须**完成当前阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要略过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪（stack traces）
   - 记录行号、文件路径、错误代码

2. **稳定复现问题**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 它是否每次都会发生？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 哪些变更可能导致了这个问题？
   - Git diff、最近的提交
   - 新依赖项、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（例如 CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断 instrumentation（检测代码/日志）：**

   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   运行一次以收集证据，显示问题发生在何处
   然后分析证据以识别失败的组件
   随后调查该特定组件
   ```

   **示例（多层系统）：**

   ```bash
   # 第 1 层：工作流
   echo "=== 工作流中可用的 Secrets: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== 构建脚本中的环境变量: ==="
   env | grep IDENTITY || echo "环境中不存在 IDENTITY"

   # 第 3 层：签名脚本
   echo "=== 钥匙串状态: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这将揭示：** 哪一层失败（secrets → 工作流 ✓, 工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误出现在调用栈深处时：**

   请参阅本目录中的 `root-cause-tracing.md` 以获取完整的向后追踪技术。

   **简要版本：**
   - 错误值起源于何处？
   - 是谁用错误值调用了这个函数？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而非在症状处修复

### 第二阶段：模式分析

**在修复之前找到模式：**

1. **寻找正常工作的示例**
   - 在同一代码库中定位类似的正常工作代码
   - 哪些与出错部分相似且能正常工作？

2. **与参考实现对比**
   - 如果正在实现某种模式，请**完整**阅读参考实现
   - 不要略读——逐行阅读
   - 在应用之前充分理解该模式

3. **识别差异**
   - 正常工作部分与出错部分有何不同？
   - 列出每一个差异，无论多么微小
   - 不要假设“那应该不重要”

4. **理解依赖关系**
   - 这需要其他哪些组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述：“我认为 X 是根本原因，因为 Y”
   - 写下来
   - 具体明确，避免模糊

2. **最小化测试**
   - 做出**最小**可能的更改来测试假设
   - 一次只改变一个变量
   - 不要同时修复多个问题

3. **在继续之前验证**
   - 生效了吗？是 → 进入第四阶段
   - 没生效？形成**新**假设
   - **不要**在此基础上叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 寻求帮助
   - 进行更多研究

### 第四阶段：实施

**修复根本原因，而非症状：**

1. **创建失败的测试用例**
   - 尽可能最简单的复现步骤
   - 如果可能，编写自动化测试
   - 如果没有框架，编写一次性测试脚本
   - **必须**在修复前拥有此测试
   - 使用 `superpowers:test-driven-development` 技能来编写正确的失败测试

2. **实施单一修复**
   - 针对已识别的根本原因
   - 一次只做**一个**更改
   - 不进行“既然都在这儿了”式的改进
   - 不进行捆绑式重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏吧？
   - 问题真的解决了吗？

4. **如果修复无效**
   - **停止**
   - 计数：你尝试了多少次修复？
   - 如果 < 3 次：返回第一阶段，利用新信息重新分析
   - **如果 ≥ 3 次：停止并质疑架构（见下文步骤 5）**
   - 在进行架构讨论之前，**不要**尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同地方揭示了新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实施
   - 每次修复都在其他地方产生了新的症状

   **停止并质疑基础：**
   - 这种模式在根本上健全吗？
   - 我们是否只是“凭惯性死守”？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前，与你的人类伙伴讨论**

   这**不是**假设失败——这是架构错误。

## 危险信号 - 停止并遵循流程

如果你发现自己有以下想法：

- “先快速修复一下，稍后再调查”
- “试着改一下 X 看看是否有效”
- “添加多个更改，然后运行测试”
- “跳过测试，我会手动验证”
- “可能是 X，让我修好它”
- “我不完全理解，但这可能有效”
- “模式说是 X，但我会以不同方式适配”
- “主要问题如下：[列出修复方案而未进行调查]”
- 在追踪数据流之前就提出解决方案
- **“再试一次修复”**（当已经尝试过 2 次以上时）
- **每次修复都在不同地方揭示新问题**

**以上所有情况均意味着：停止。返回第一阶段。**

**如果 3 次以上修复失败：** 质疑架构（参见第四阶段第 5 步）

## 你的人类伙伴发出的“你做错了”信号

**留意这些纠正指示：**

- “那不是没发生吗？” - 你在未验证的情况下做了假设
- “它会向我们展示……吗？” - 你应该添加证据收集步骤
- “停止猜测” - 你在不理解的情况下提出修复方案
- “深入思考这个（Ultrathink this）” - 质疑基础，而不仅仅是症状
- “我们卡住了？”（沮丧语气） - 你的方法行不通

**当你看到这些时：** 停止。返回第一阶段。

## 常见的自我合理化借口

| 借口                                | 现实                                              |
| ----------------------------------- | ------------------------------------------------- |
| “问题很简单，不需要流程”            | 简单问题也有根本原因。对于简单 bug，流程很快。    |
| “紧急情况，没时间走流程”            | 系统化调试比盲目试错**更快**。                    |
| “先试试这个，然后再调查”            | 第一次修复奠定了模式。从一开始就要做对。          |
| “确认修复有效后我再写测试”          | 未经测试的修复站不住脚。先测试才能证明有效性。    |
| “一次性修复多个问题节省时间”        | 无法隔离哪个起了作用。会导致新 bug。              |
| “参考太长，我会适配模式”            | 部分理解必然导致 bug。完整阅读它。                |
| “我看到问题了，让我修好它”          | 看到症状 ≠ 理解根本原因。                         |
| “再试一次修复”（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段            | 关键活动                           | 成功标准                 |
| --------------- | ---------------------------------- | ------------------------ |
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解**什么**和**为什么** |
| **2. 模式**     | 寻找正常示例、对比                 | 识别差异                 |
| **3. 假设**     | 形成理论、最小化测试               | 确认或形成新假设         |
| **4. 实施**     | 创建测试、修复、验证               | Bug 解决，测试通过       |

## 当流程揭示“无根本原因”时

如果系统化调查揭示问题确实是环境相关的、依赖时序的或外部的：

1. 你已完成该流程
2. 记录你调查的内容
3. 实施适当的处理机制（重试、超时、错误消息）
4. 添加监控/日志以便未来调查

**但是：** 95% 的“无根本原因”案例都是调查不完整所致。

## 支持性技术

这些技术是系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** - 沿调用栈向后追踪 bug 以找到原始触发点
- **`defense-in-depth.md`** - 在找到根本原因后，在多层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替换任意超时

**相关技能：**

- **superpowers:test-driven-development** - 用于创建失败的测试用例（第四阶段，步骤 1）
- **superpowers:verification-before-completion** - 在宣称成功之前验证修复是否生效

## 现实世界的影响

来自调试会话的数据：

- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时的盲目试错
- 首次修复成功率：95% vs 40%
- 引入的新 bug：接近零 vs 常见
